## 证据能说明什么

两个不同公网目标同时短暂超时，而本地网关有响应，比单一目标偶发不回 ICMP 更能支持外网异常；结合游戏错误、DNS 事件和战网重连，用户的网络波动判断有依据。现有记录不能进一步区分路由器 WAN、运营商、上游路径或当前路由软件的问题，也不能证明游戏服务器本身故障。虚拟网关 25.255.255.254 一直不响应，不能把它的失败当成整夜断网；另一个虚拟接口变化并未与主要故障重合。

长时段中游戏、OWNeacClient 的 PID 和创建时间未变，窗口仍响应。02:38–03:06 的多次进程更换伴随人工操作，不标成自动崩溃。游戏日志部分读取失败为文件占用（错误 32），不代表日志内容没有错误。

记录到的 Shift 边沿不能证明脚本停了：20 ms 脉冲可能漏采样，`GetAsyncKeyState` 在桌面、权限或前台访问受限时也可能返回零，见 [微软接口说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate)。原 PowerShell 脚本与只读记录器可以并行；截图不会拦截它的按键。不过画面已证明出现过不活跃警告，有效对局统计和活动判定仍需后续处理。

该程序在部分死斗模式分支（模式 1/5）中，通过游戏窗口和画面颜色判断；约 120 秒未得到预期状态或窗口异常后，结束 NeacLoader.exe 进程树，再对已打开并登录的战网窗口截图、查蓝色按钮并发送点击，固定等约 15 秒。托比昂模式 2/6 没有同等的持续重启分支。它并不完整处理关闭状态的战网启动、账号重新认证或重回指定自定义房间。

原程序还存在条件性 VMware 防火墙处理、宿主加载等旁支；新版只参考其“退出后由战网启动”的流程，未复制这些行为。

## 0.3.0 已实现

“重启游戏”按钮与自动恢复共用一条流程：检查路径及启动识别配置 → 关闭核验过的游戏并等待退出 → 仅清理配置路径对应的残留 OWNeacClient.exe → 打开/识别战网 → 核对守望先锋标志和“进入游戏”文字后点击 → 等待游戏窗口 → 按已识别页面导航回最稳轮换版。

直接回到自定义浏览页时，识别目标模式并重新选择、加入；不需要为了进房先重启。蓝色错误画面需要标志、错误文字、按钮区域同时匹配，持续 90 秒才重启；普通加载或短暂回大厅不计入。游戏进程缺失、窗口持续无响应沿用原来的恢复规则，每小时最多 3 次。

针对战网恢复网络后弹出遮挡的问题，启用预设、自动恢复且非演练时，遮挡连续 5 秒会尝试一次切回游戏。Windows 若拒绝切换，仍需手动切回；没有对其他应用循环抢焦点。

验证包括：239 张原始截图、原尺寸还原样本、流程参考和错误模式/按钮负例，共 449 项 C++ 回放检查，零不符合预期；另 122 项擦除错误文字的负例均未触发重启。四套 CTest 通过，涵盖目标选择证据、配置保存、战网主窗口选择、停止/旧代次拒绝输入和专用测试子进程退出。还原图片来自缩略图，不等于独立实机分辨率测试；部分对局帧允许保持未知，因为 HUD 会变化。

真实点击、残留清理、战网启动到授权后进房尚需在本机走一遍。NeacProtect 每次授权仍由用户处理，当前版本不能承诺掉线后的全程无人值守。预设布局或模式排序变化时也可能停在 UNKNOWN，可用手动校准补充。具体试用见 [新版步骤](QUICKSTART.zh-CN.md#这次先测试重启游戏)。
